刚开始接触 Agent 框架时，我容易把 MoFA、LangChain 和 LangGraph 放在同一个列表里比较：哪个 API 更简单，哪个工具更多，哪个例子更完整。这样很快会记住很多名字，却仍然说不清一个 Agent 系统到底怎样运行。

后来我发现，更有用的问题是：

> **谁决定下一步做什么？状态由谁保存？一个 Agent 如何运行，与多个 Agent 如何组合，分别由什么机制负责？**

先给一个简化结论：

- **LangChain** 偏应用开发层：把模型、工具、提示词与中间件组成常见的 Agent 应用。
- **LangGraph** 偏运行时与编排层：用状态和图明确描述执行步骤、分支、循环与暂停恢复。
- **MoFA** 偏组件组合层：把 Agent、代码和服务作为可连接单元，通过数据流组织成更大的系统。

这不是说三者完全不能做彼此的事。它们的抽象重点不同，实际项目中也可以组合。

## 先分清几个概念

**Workflow（工作流）** 描述一组步骤如何衔接。步骤顺序可以固定，也可以包含条件分支。

**Agent Loop（Agent 循环）** 描述模型如何利用目标与状态选择行动、调用工具、观察结果，再决定继续还是结束：

~~~text
目标与状态 → 模型选择行动 → 工具执行 → 新观察
    ↑                              │
    └────── 根据结果继续或结束 ─────┘
~~~

**Dataflow（数据流）** 描述数据从哪里产生、依赖什么输入、流向哪些组件，关注组件间的数据依赖和连接方式。

**State（状态）** 是任务执行中需要保留的信息，例如消息历史、工具结果、当前阶段、重试次数和完成条件。**Graph（图）** 用节点表达执行步骤、用边表达下一步去向；状态会在节点间传递或更新。

这些概念相关，却不等价。数据流可以承载 Agent，工作流也可以嵌入 Agent Loop；但“节点能相连”不会自动说明循环由谁控制、状态如何更新、什么时候算完成。

## 一张表先看定位

| 维度 | LangChain | LangGraph | MoFA |
| --- | --- | --- | --- |
| 主要问题 | 怎样快速组装 LLM 应用与 Agent | 怎样精确控制有状态的执行过程 | 怎样把 Agent 与服务组合成系统 |
| 常见抽象 | 模型、工具、提示词、中间件、Agent | State、Node、Edge、条件边、Checkpoint | Agent/节点、输入输出端口、Dataflow |
| 执行结构 | 预置的模型与工具循环 | 显式状态图，可有分支和循环 | 组件通过数据连接组合，由运行时调度 |
| 工具调用 | Agent 选择并调用注册的工具 | 工具可作为图节点，路径由图控制 | 工具或 Action Agent 可作为连接组件 |
| 更适合 | 快速开发对话、检索和工具 Agent | 长任务、复杂控制、持久状态、人类介入 | 多组件复用、跨进程或分布式的数据流组合 |
| 需要留意 | 高层抽象会替你处理不少控制细节 | 要自行设计状态与图，学习成本更高 | 组件组合清晰，推理循环通常放在 Agent 内部 |

“更适合”是学习与架构上的判断，不是能力边界。实际选型还要看框架版本、运行时、部署要求和团队熟悉度。

## LangChain：先把 Agent 应用搭起来

LangChain 提供模型、工具、提示词和中间件等构件。它的高层 Agent API 会把这些构件组织成常见的模型与工具循环：模型收到上下文后，可能直接回答，也可能提出工具调用；工具执行结果进入后续模型步骤，直到结束条件满足。

以“查资料并给出总结”为例，可以给 Agent 注册搜索工具。Agent 根据请求决定是否搜索，执行后查看结果；如果信息不够，再发起下一次搜索。

它的优势是起步快、集成多、常见 Agent 用法容易表达。代价是，当执行过程需要复杂分支、循环条件、暂停恢复或逐节点审计时，高层 API 可能不再是最清楚的表达方式。这时可以下沉到 LangGraph。

一个重要事实是：**LangChain 的 Agent 并不是与 LangGraph 完全独立的另一套底层执行引擎。** 当前官方文档把 LangChain 定位为 Agent framework，并说明其 Agent 抽象构建在 LangGraph 之上。日常开发可以先使用高层能力，需要更细控制时再使用 LangGraph。

## LangGraph：把执行路径和状态写明白

LangGraph 的重点不是“多画几个节点”，而是把运行时控制结构明确下来。一个图通常包含：

- **State**：当前任务的数据，例如消息、搜索结果和步骤状态；
- **Node**：执行一项工作，例如调用模型、运行工具或做校验；
- **Edge**：规定执行后去哪个节点；
- **Conditional Edge**：根据状态选择下一条路径；
- **Checkpoint**：保存进度，以便继续运行或处理中断。

同一个“查资料”任务可以这样表示：

~~~text
START → Agent → Tools → Agent ──→ END
                  ↑       │
                  └───────┘
~~~

Agent 节点生成工具调用时进入 Tools；工具结果写回 State 后，流程回到 Agent。若没有工具调用或已满足完成条件，流程走向 END。循环成为图结构和状态更新的一部分，而不是隐藏在一串调用里。

LangGraph 的优势是控制关系可见。开发者可以规定哪些步骤确定执行、哪些步骤交给模型，也可以在关键点暂停、等待人工确认、从检查点恢复。它适合长任务、复杂业务流程和需要检查中间状态的应用。

代价也很直观：开发者要想清楚 State 包含什么、节点职责是什么、条件边如何判断、错误与重试如何处理。若只是“模型调用一个工具并回答”，直接使用 LangChain 的高层 Agent API 往往更省力。

## MoFA：把 Agent 当作可组合的系统组件

MoFA 让我想到的核心问题是：**怎样把多个不同职责的 Agent 或服务组合起来，而不是把所有能力都塞进一个大 Agent。**

在基于 Dora-RS 的 MoFA 概念文档中，Agent 可以由数据流节点组成，节点通过数据连接接收输入并输出结果。例如：

~~~text
用户输入
  ↓
检索 Agent
  ↓
推理 Agent
  ↓
校验 Agent
  ↓
结果输出
~~~

每个组件有自己的职责、实现和依赖，组合时关注输入输出和数据依赖。这让组件更容易复用，也适合需要跨进程或分布式运行的系统。

这里要澄清一个容易过度简化的说法：

> **MoFA 不是“做不了推理循环”；而是显式控制一个 Agent 的推理循环，不是它最自然、最突出的系统级抽象。**

MoFA 官方概念文档列出了 Reflection、Actor、ReAct 等 Agent 设计模式，也提到了 self-refine 组合 Agent。因此，循环可以存在于某个 Agent 内部，也可以通过组件连接形成回路。真正的差别在于：如果我需要精确控制“每一步根据什么状态选下一步、循环几次、何时暂停、失败后如何恢复”，LangGraph 的 State + Graph 通常更直接；如果我要管理多个 Agent 如何交换数据、构成服务，MoFA 的 Dataflow/Composition 思路更贴切。

还要留意版本边界：MoFA 相关公开资料目前能看到不同实现脉络。mofa.ai 的概念文档介绍 Dora-RS Dataflow；mofa-org/mofa 当前主仓库则介绍 Rust 微内核、插件和工作流引擎。上面关于“组件组合”的讨论是在架构层面归纳，不代表所有 MoFA 仓库共享同一套 API 或运行细节。实际选型前应先确认具体仓库和版本。

## 把优缺点换成工程问题

### LangChain：高层组装方便，控制细节可以下沉

适合先做一个可用的对话 Agent，接入模型、工具或检索组件，验证产品流程和工具设计。要权衡的是：循环和条件越来越复杂时，高层 API 不一定最容易解释执行过程；任务状态、权限、调用预算和结束条件仍然需要应用自己明确。

### LangGraph：显式编排能力强，图和状态要认真设计

适合多轮工具调用、长任务、复杂分支、暂停恢复和人工审批。代价是学习曲线更陡；State 和节点切分不合理会让图难读，简单问题用图建模也可能徒增复杂度。

### MoFA：组件与数据流清楚，系统边界更重要

适合多个 Agent 或服务各自有独立职责、需要复用替换或跨进程交换数据的场景。需要定义稳定的输入输出和运行时边界；分布式调用、数据格式和故障处理也会带来额外成本。如果主要难点是单个 Agent 的反复判断和循环控制，就要额外设计内部运行逻辑，或交给更适合显式编排的运行时。

## 三者能不能组合？

可以，但要先决定谁负责哪一层，尤其避免多个框架同时争夺同一段执行循环和状态。一种清楚的分工是：

~~~text
MoFA Dataflow：负责 Agent / 服务之间的数据组合
             ↓
LangGraph：负责一个任务执行过程中的状态与循环控制
             ↓
LangChain：提供模型、工具与高层 Agent 构件
~~~

例如，外层 MoFA 负责接入文件、检索服务和结果存储；其中一个“研究 Agent”由 LangGraph 控制循环；LangChain 提供模型和搜索工具的适配。

这只是可能的架构，不是建议每个项目都堆三套框架。框架之间可能通过语言接口、HTTP 或消息总线连接，实际接口要自己适配。先明确四件事：

1. **谁拥有任务状态？** 避免 LangGraph 与外层调度器维护冲突的进度。
2. **谁拥有 Agent Loop？** 一个任务的循环要有清楚的控制者，方便定位停止条件。
3. **组件之间传什么？** 尽量传结构化请求、结果和错误，而不是依赖隐式共享上下文。
4. **谁验证最终完成？** 由业务逻辑或验收节点检查，不要只让模型回答“已完成”。

系统规模不大时，先用 LangChain 或 LangGraph 单独做一个闭环；等到组件复用和分布式需求明确后，再考虑 MoFA，通常更容易看清架构成本。

## 怎么学，才能建立架构直觉？

可以用同一个小任务练习，例如“搜索三个来源，整理答案，并检查是否有证据支持”：

1. **先手写最小循环**：读入目标 → 模型选工具 → 执行工具 → 记录结果 → 再决定或结束。看清每个部件由谁负责。
2. **用 LangChain 重做**：观察高层 API 替你封装了哪些模型、工具和循环逻辑。
3. **用 LangGraph 重做**：把状态、Agent 节点、工具节点、条件边和结束条件逐个画出。
4. **用 MoFA 重做外层组合**：把输入、检索、推理、校验和输出拆成组件，通过数据依赖连接。
5. **比较故障处理**：让工具超时、返回空结果或报错，检查状态是否保留、下一步由谁决定、何时结束。

看源码或教程时，也可以用四个问题做阅读提纲：

- **控制流在哪里？** 谁决定下一个节点或动作？
- **状态在哪里？** 工具返回后写到哪里，下一步能否读取？
- **副作用在哪里？** 工具由谁执行，权限与重试怎么处理？
- **停止条件在哪里？** 完成、预算用尽或需要人工介入时会发生什么？

这样学下来，关注点就不再是“哪个框架更像真正的 Agent”，而是能把架构需求映射到恰当的抽象上。

## 结语

我现在用三句话记它们：

> **LangChain 帮我搭 Agent 应用；LangGraph 帮我明确 Agent 怎么运行；MoFA 帮我组合 Agent 与服务。**

如果我关心单个 Agent 如何根据反馈继续行动，我会优先研究 **Agent Loop、State 和 LangGraph**；如果我关心多个能力模块如何交换数据并形成系统，我会重点看 **MoFA 的 Dataflow 与 Composition**；如果我还在验证一个 Agent 的基本形态，**LangChain** 可以让我更快开始。

工具会变，API 会变，但“控制流、状态、组件边界、停止条件”是理解 Agent 架构时更稳定的学习坐标。
